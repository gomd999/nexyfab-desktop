# AI 입력 경로 성능 실측과 결함 보고 (2026-07-31)

> 텍스트 · 사진/스케치 · 2D 벡터도면 · 2D 이미지도면 **네 입력 경로**를 실측하고,
> 그 과정에서 드러난 결함 6종을 정리한다.
> 대상 코드: `scripts/drawing-to-3d/` · `src/lib/ai/` · `src/lib/cad-ir/`
> 관련 문서: [`drawing-to-3d-methodology.md`](./drawing-to-3d-methodology.md)

---

## 0. 한 줄 요약

**성능보다 계측기가 먼저 틀려 있었다.** 「타입 분류 56%」는 정확도가 아니라 *못 잰 것을 오답으로 센 값*이었고,
실제로 측정된 것은 100%였다. 계측기를 고친 뒤 네 경로를 다시 재고, 그 과정에서
**총점이 부분 실패를 가리는 형태**의 결함을 다섯 곳에서 더 찾았다.

---

## 1. 왜 이 문서인가

측정을 시작하기 전 상태는 다음과 같았다.

| 경로 | 정확도 측정 |
|---|---|
| 2D 이미지도면 → 3D | 있음 — 그러나 **분모가 틀림** |
| 텍스트 → 3D | 게이트 통과 여부만. **치수를 대조하지 않음** |
| 2D 벡터도면 → 3D | 합성 픽스처 1장. 실도면 0장 |
| 사진/스케치 → 3D | **0건** (테스트는 전부 배선·파싱, 모의 LLM) |

「측정이 없다」와 「측정이 틀렸다」는 둘 다 **성능을 모른다**는 뜻이고, 후자가 더 나쁘다 —
모른다는 사실조차 가려지기 때문이다.

## 2. 실측 결과

배포본(`20260802-202`) 기준. LLM 은 실행마다 흔들리므로 **단일 실행 값**임을 명시한다.

### 2.1 2D 이미지도면 → 3D (평가셋 50장 = 깨끗 25 + 스캔열화 25)

제품이 실제로 쓰는 **웹 경로**(`extractDrawingFromImage`, 11어휘·분류→치수 2단계):

| 항목 | 값 |
|---|---|
| 측정 완결 | 50/50 |
| 타입 분류 | 49~50/50 (98~100%) |
| 파라미터(±0.5mm) | 206/220 (93.6%) |
| 구멍 위치(±1mm) | 26/26 (100%) |
| 기하 게이트 | 49/50 (98.0%) |

> 위 값은 **최종 구성(추정 선언 + 부위별 역투영) 실행**이다. 그 직전 실행은
> 파라미터 212/220(96.4%) · 게이트 50/50 이었다. **두 실행의 차이는 개선/악화가 아니라
> LLM 의 실행 간 편차**로 보는 것이 맞다 — 8~10건 규모의 오독을 다루는 구간에서
> 1~2건 차이는 유의하지 않다. 회귀 판단은 **여러 실행**을 봐야 한다.

비교 — CLI 경로(`extractDrawing`, 5어휘·단일콜): 파라미터 88.8% · 게이트 79.6% · 측정 49/50.

### 2.2 텍스트 → 3D (고정 8케이스, 5개 도메인)

| 항목 | 값 |
|---|---|
| 게이트 통과 | 8/8 |
| **명시 치수 재현율** | 23~24/24 (95.8~100%) |
| 단위 환산(3m→3000) | 전부 정확 |
| 지연 | p50 9.3s · p90 **18.3s** (개선 전 p90 99.2s) |

> ⚠ 재현율은 **축 배정을 검증하지 않는다**. `300x200` 같은 표기는 원문 자체가 축을 확정하지
> 않으므로, 가로/세로 뒤바뀜은 이 지표로 잡히지 않는다. 원문이 정하지 않은 것을 정답으로 삼지 않는다.

### 2.3 2D 벡터도면(DXF) → 3D (로컬 코퍼스 실도면 16장)

| 항목 | 값 |
|---|---|
| 인입 성공 | 16/16 (100%) |
| 왕복 검증 PASS | 14/16 (87.5%) |
| 왕복 FAIL(오해석) | **0** |
| UNAVAILABLE(증거 부족) | 2 — **통과가 아니다** |
| **포착 범위(중앙값)** | **0%** |

> **포착 범위 0%가 이 경로의 정직한 헤드라인이다.** 87.5% PASS 는 「치수·원·범위가 살아남았다」이지
> 「도면을 3D 로 만들었다」가 아니다. 실도면은 POLYLINE·ARC·SPLINE·INSERT 로 그려지는데
> 우리 2D IR 은 LINE·CIRCLE·DIMENSION 만 재현한다. 이 경로는 **판독 보조**이지 생성이 아니다.

### 2.4 사진/스케치 → 3D (합성 픽토리얼 48장)

| 항목 | 값 |
|---|---|
| 측정 완결 | 48/48 (개선 전 8/24) |
| 형상 판별 | 45/48 (93.8%) |
| 절대 치수(치수 표기 有) | 48/62 (77.4%) |
| **비율(치수 표기 無)** | 49/77 (**63.6%**) |
| 추정 고지(프롬프트 계약) | 24/24 (100%) |
| **치수 출처 신고 정확도** | **48/48 · 과대신고 0** |

조건별 — 같은 GT·같은 그림, 조건만 다름:

| 조건 | 형상 | 절대 치수 | 비율 |
|---|---|---|---|
| clean(깨끗) | 95.8% | 74.2% | 70.0% |
| photo(사진 조건) | 91.7% | **80.6%** | 56.8% |

> **병목은 이미지 품질이 아니라 판독 자체다.** 원근 기울임·방향성 조명·잡음·JPEG 압축을
> 입혀도 성능이 거의 안 깎인다.
>
> ⚠️ **`photo` 는 실사진이 아니다.** 재현한 것: 원근 대용 전단 · 조명 기울기 · 센서 잡음 · 흐림 · 압축.
> 재현 못한 것: 재질 반사 · 그림자 · 초점 흐림 · 배경 물체.
> 이 버킷이 답하는 질문은 「사진에서의 성능」이 아니라 **「이미지가 깨끗하지 않을 때 성능이 유지되는가」**다.
> 두 질문은 다르고, 섞어 말하면 실사진 성능을 주장하는 셈이 된다.

## 3. 발견한 결함 6종

전부 같은 뿌리를 갖는다: **하나로 뭉친 숫자가 부분 실패를 가린다.**

### 3.1 미측정을 오답으로 셌다 — 계측기 결함

```
종전 보고:  typeClassification 28/50 (56.0%)
실제:       22건은 Gemini 503·JSON 절단으로 **판독 자체가 안 됨**
            측정된 28건은 28/28 (100%)
            plate_with_holes·l_bracket 은 표본 0인데 "type 0/5" 로 적혀 전부 틀린 것처럼 보였다
```

구별해야 할 세 상태 — **뭉치면 어느 쪽도 알 수 없다**:

> 측정했고 맞음 · 측정했고 틀림 · **측정 자체가 안 됨**

수정: `run-e2e.mjs` 가 측정된 것만 분모로 쓰고, 미측정은 사유별(일시/영구/절단)로 따로 센다.
표본 0인 버킷은 「0%」가 아니라 **「표본 없음」**으로 적는다.

부수 효과 — 지난 「파라미터 95.0%」는 분모가 139였다. 지금 88.8~96.4% 는 분모가 215~220 이다.
**내려간 것이 아니라 분모가 늘었다.** 살아남은 케이스만 센 값은 개선이 아니라 선택 편향이다.

### 3.2 절단이 어디서도 보이지 않았다 — 계통

제공자 **11곳**(텍스트 7 + vision 4) 중 **어느 곳도 `finish_reason` 을 읽지 않았다.**
그래서 응답이 잘려 도착해도 호출부에는 「형식이 이상하다」로만 보였다. 오늘 두 번 물렸다:

```
imageIntentFromSketch  maxTokens 500   → 24장 중 16장 NON_JSON (원인은 전부 절단)
from-text 어셈블리      maxTokens 16384 → bad JSON → 느린 모델 폴백(지연 12배)
```

**증상은 파싱 실패였지만 원인은 자리 부족이었고, 대응은 정반대다:**

| 원인 | 대응 |
|---|---|
| 형식 위반 | 프롬프트를 손본다 |
| **절단** | **출력 상한·thinking 을 조정한다** |

수정: `src/lib/ai/providers/truncation.ts` 를 만들어 11곳 배선. 세 상태를 구별한다.

```
true       제공자가 절단이라고 말했다
false      제공자가 정상 종료라고 말했다
undefined  제공자가 아무 말도 안 했다   ← false 가 아니다
```

모르는 것을 `false` 로 채우면 「안 잘렸음이 확인됐다」로 읽힌다 — 그건 거짓이다.

### 3.3 측정한 것과 배포한 것이 갈려 있었다

같은 평가셋으로 두 추출 경로를 나란히 재니:

```
extractDrawing         (5어휘·단일콜)   파라미터 88.8% · 게이트 79.6% · 측정 49/50
extractDrawingFromImage(11어휘·2단계)  파라미터 96.4% · 게이트  100% · 측정 50/50
```

웹은 이미 2단계를 쓰는데 **MCP 서버만 단일콜**이었다 — 클로드에서 도면을 읽히는 사용자가
더 나쁜 경로를 타고 있었고, 어휘도 11종 중 5종만 고지됐다. MCP 를 2단계로 옮겼다
(역투영 diff 검증이 따라온다).

### 3.4 총점이 오르면서 위험한 실패가 늘었다

```
단일콜 오독 22건 = 결측 16(정직한 공백) + 오답  5
2단계  오독  8건 = 결측  1            + 오답  7   ← confidence 1 짜리 오답
```

2단계 스키마는 모든 치수를 `required` 로 두고 프롬프트가 「없으면 추정」을 지시한다 —
**「못 읽었다」고 말할 자리가 없었다.** `l_bracket` 두께(정답 4mm)가 5·6·10 으로 확신에 차서 틀렸다.
총점만 보면 개선인데 **틀린 3D 가 나가는 쪽은 늘어난 것**이다.

수정: 모델이 추정한 필드를 스스로 선언(`estimatedFields`)하게 하고, 선언되면 confidence 를 0.6 으로 강등.

| 지표 | 값 |
|---|---|
| 포착(틀린 값 중 표시된 비율) | 7/11 (63.6%) |
| **오경보(맞은 값 중 표시된 비율)** | **1/206 (0.5%)** |

표시된 것은 전부 「못 읽어서 추정」이었고, 표시 안 된 4건은 「인쇄된 숫자를 읽고 오독」이었다.
**두 실패는 성격이 다르고 대응도 다르다** — 전자는 고지·되묻기로, 후자는 교차검증으로.

> ⚠ 포착 63.6% 는 100% 가 아니다. **깃발이 없다고 「확실하다」는 뜻이 아니다.**

### 3.5 뭉친 평균이 묵은 좌표 버그를 가리고 있었다

D1 역투영은 지지율을 **하나로 뭉친 평균**으로만 봤다. 부위별로 나누자
**GT 정답 intent 의 구멍 지지율이 0%** 로 나왔다:

> 도면 TOP VIEW 는 좌하단 원점·**+y 위**인데 이미지 좌표는 **+y 아래**다.
> 사각 외곽은 상하 대칭이라 뒤집혀도 티가 안 났고, **구멍만 어긋났다.**
> 전체 평균 0.80(문턱 0.6)에 희석돼 **한 번도 드러나지 않았다.**

`plate_with_holes` · `base_plate` 양쪽 수정. 역투영 실효도 처음 쟀다:

| 지표 | 값 |
|---|---|
| 포착(오독 있는 케이스 중 DEMOTE) | 2/11 (18.2%) |
| 오경보(전부 맞은 케이스 중 DEMOTE) | 2/39 (5.1%) |

약하다. 과장하지 않고 수치로 남긴다.

### 3.6 정직한 신호가 사용자에게 닿지 않았다

추출기는 못 읽은 치수(`missingFields`)와 추정한 치수(`estimatedFields`)를 구별해 내보내고 있었다.
그런데 라우트가 **confidence 숫자만 옮기고 어느 치수인지 버렸고**, 화면은 「신뢰도 60%」만 보여 줬다 —
**무엇을 확인해야 하는지 알 수 없다.** 응답·화면 양쪽에 실었다(6개 국어).

> ⚠ 치수 이름(`width`·`thickness`…)은 **번역하지 않는다** — 그 이름 그대로 3D 파라미터·견적·도면에
> 쓰이므로, 화면에서만 다른 말로 부르면 사용자가 대조할 수 없다.

## 4. 재사용 가능한 결과

### 4.1 치수선 판독 하한 — 실측

| 주기 방식 | 치수선 길이 | 판독 |
|---|---|---|
| 치수선 | 9.6 px | **0/6** |
| 치수선 | 14.4 px 이상 | **4/4** |
| 텍스트 `t=` 주기 | (해당 없음) | **10/10** — 두께 1.5mm 도 |

`l_bracket` 두께 6/6 미판독의 원인은 모델이 아니라 **9.6px 짜리 치수선**이었다.
같은 판독기·같은 도면 양식에서 **주기 방식만 다른데 0% 대 100%** 로 갈렸다.

**얇은 치수는 치수선으로 그리지 말고 지시선 주기로 쓴다.**
코드: `src/lib/drawing/dimensionLegibility.ts`.

> ⚠ 9.6 과 14.4 **두 점만** 실측했다. 그 사이는 재지 않았으므로 `legible` 로도 `illegible` 로도
> 말하지 않고 `unverified` 로 둔다. 임계를 하나로 뭉개면 「10.0px 는 읽힌다」는 근거 없는 주장을
> 코드가 하게 된다.

### 4.2 등각 단축 — 원인은 찾았고 고치지는 못했다

비율 오차가 전부 한 방향이고 배율이 일관됐다:

```
diameter 60%→31% (0.52x)   width 71%→33% (0.46x)
webThickness 6%→3% (0.50x) thickness 17%→8% (0.47x)
```

**~0.5 = sin(30°)** — 모델이 **투영된 겉보기 길이를 실제 길이로** 읽었다.
세로 방향(height·length)만 정확한 것과 정확히 들어맞는다.

프롬프트에 단축 보정을 지시(v1.1.0). 결과:

| 실행 | 대상 | 형상 | 비율 |
|---|---|---|---|
| 지시 전 | 48장 | 93.8% | 53.8% |
| 지시 후 | plain 24장 | 100% | 55.0% |
| 지시 후(+`dimensionSource`) | 48장 | 93.8% | 63.6% |

**형상 판별이 오른 실행이 있으나 48장 기준으로는 93.8% 로 동일하고, 비율은 유의하게
움직이지 않았다.** 계통 편향(전부 ~0.5배)이 흩어진 오차로 바뀌었을 뿐이다.
표본 48장·단일 실행으로는 **개선을 주장할 수 없다** — 고친 척하지 않는다.
단축 보정 지시 자체는 **사실로서 옳으므로** 남겨 두되, 효과는 미입증으로 적는다.

### 4.3 못 고치는 것은 표시한다 — `dimensionSource`

치수 표기가 없는 그림의 비율 정확도는 60%대다. 그 사실이 산문 `summary` 에만 있어
**하류 코드가 구별할 수 없었고**, 추정치가 그대로 3D·견적으로 흘러갔다.

모델이 `callouts` / `inferred` / `mixed` 를 신고하게 하고 응답·캐시에 실었다.

| 지표 | 값 |
|---|---|
| 신고 정확도 | **48/48 (100%)** |
| **과대신고(추정을 「읽었다」)** | **0** |

**비율은 못 고쳐도 「믿어도 되는 값인가」는 정확히 전달된다.**
하네스가 과대신고 0 을 잠근다 — 그것이 이 경로의 최악(55% 정확도 추정치가 측정치로 승격돼
제작에 흘러가는 것)을 막는 유일한 방어다.

### 4.4 지연 — 상한을 관측값 위에 놓는다

```
정상 응답 출력 토큰:  73 · 80 · 103 · 276 · 477 · 633 · 1540   ← 관측 최대 1,540
설정된 상한:          16,384                                   ← 10배 여유
폭주 회차:            16,384 전부 소진 → 약 55초 낭비 후 MAX_TOKENS → 느린 모델 폴백
```

두 단계로 고쳤다:

1. **MAX_TOKENS 면 같은(빠른) 모델로 스키마 없이 한 번 더.** 느린 모델 폴백은 마지막 수단.
   → p90 99.2s → 65.1s
2. **스키마 회차 상한을 관측 최대의 2배(3,072)로.** 폭주가 5배 빨리 드러난다.
   → p90 **18.3s**

정확도 불변(게이트 8/8 · 명시 치수 23/24).

> ⚠ 정상적으로 큰 어셈블리가 낮아진 상한에 걸려도 **실패하지 않는다** — 스키마 없는 회차로
> 넘어가 성공한다(실측 1,540 토큰 케이스가 그 경로로 통과했다). 한 왕복을 더 쓸 뿐이고,
> 매번 55초를 버리는 것보다 싸다.

## 5. 계측기 자체의 결함 — 두 번

**측정 도구를 먼저 의심한다**는 규약이 이번에도 두 번 맞았다.

1. **`run-e2e.mjs`** — 미측정을 오답으로 셈 (§3.1).
2. **`gen-sketch.mjs`** — 얇은 치수를 `max(8px, …)` 로 **화면에서만** 두껍게 그렸다.
   그러면 그림이 보여 주는 비율과 정답 비율이 달라진다. 그 상태로 하마터면
   「모델이 얇은 피처를 과소 판독한다」고 적을 뻔했다 — 실제로는 **우리가 다른 그림을 보여 주고
   원래 숫자로 채점한 것**이다.
   → 클램프를 걷고, **GT 를 그림이 표현 가능한 값으로 올린 뒤 그 값을 정답으로 쓴다.**
   (값을 올려 놓고 올리기 전 값으로 채점하면 같은 배신이다.)

또한 픽토리얼 생성기에서 **캔버스 밖으로 잘린 그림**과 **속이 비쳐 보이는 uChannel**(압출 측면 미렌더)을
눈으로 확인해 고쳤다. 그림이 형상으로 안 보이면 재는 것은 모델의 판독력이 아니라 **우리 그림 실력**이다.

## 6. 하네스 사용법

| 하네스 | 대상 | 실행 |
|---|---|---|
| `scripts/drawing-to-3d/run-e2e.mjs` | 2D 이미지도면 (50장) | `node run-e2e.mjs --web` (제품 경로) · `--only <substr>` |
| `scripts/drawing-to-3d/text-eval.mjs` | 텍스트 (8케이스) | `node text-eval.mjs [--repeat N]` |
| `scripts/drawing-to-3d/gen-sketch.mjs` | 사진/스케치 평가셋 생성 | `node gen-sketch.mjs [count] [seed]` |
| `src/lib/ai/sketchIntentEval.test.ts` | 사진/스케치 (48장) | `NEXYFAB_AI_LIVE=1 vitest run …` · `SKETCH_ONLY=<substr>` |
| `src/lib/cad-ir/dxfCorpusEval.test.ts` | 실도면 DXF (16장) | `vitest run …` (코퍼스 없으면 skip) |

공통 규약:

- **미측정은 오답이 아니다.** 분모에 넣지 않고 사유별로 따로 센다.
- **표본 0 은 「0%」가 아니라 「표본 없음」**이다.
- **skip 은 통과가 아니다.**
- 깃발류 지표는 **포착률과 오경보율을 함께** 보고한다 — 전부에 깃발을 꽂으면 포착 100% 지만 쓸모 0 이다.

> ⚠️ **로컬 코퍼스는 라이선스 제한(로컬 전용·재배포 금지)이다.** 하네스는 경로만 읽고
> **어떤 파일도 저장소로 복사하지 않는다.** 리포에 남는 것은 수치뿐이며, 코퍼스가 없으면
> 정직하게 skip 한다 — 그리고 skip 은 통과가 아니다.
