## 2. ★ 왜 이게 오래 살아남았나 — CI 사각지대 2건

회귀를 붙이려다 발견한 것이 결함 자체보다 중요하다.

### 2-1. MCP 엔트리는 vitest 에서 **import 조차 불가능**했다 (`dfe7c9cb`)
`mcp-server.mjs` 를 import 하면 `SyntaxError: Invalid or unexpected token`. 원인은 1행
**shebang** — node 는 `#!` 를 벗겨 실행하지만 vite 변환기는 벗기지 않는다. 즉 이 파일은
**실행은 되는데 CI 는 한 줄도 볼 수 없는** 상태였다(260727 A-5 `87a9e3f2` 와 같은 종류).
레포에 shebang 스크립트가 다수라 파일 하나를 고치지 않고 `vitest.config.ts` 에
`nf-strip-shebang` 플러그인을 뒀다. `#!` 두 글자만 `//` 로 바꿔 **줄 수·문자 오프셋 보존**
(스택트레이스 무손상). 스크립트의 실행 계약(`node mcp-server.mjs`)은 그대로.

### 2-2. pre-commit 이 `.mjs` 엔진 전체를 건너뛰고 있었다 (`81c36d42`)
훅의 vitest 단계가 스테이징 파일을 `grep -E '\.(ts|tsx)$'` 로만 골랐다. 그런데 **소비자 문서를
실제로 만드는 엔진은 전부 .mjs** 다(assembly·package·execution-gate·easy-summary·
domain-dossier-verify·dxf-export·boq·mcp-server…). 도면·BOQ·안전 판정 문서를 만드는 코드를
고치는 커밋이 **관련 테스트를 한 줄도 돌리지 않고** 통과해 왔다.
→ `.(ts|tsx|mjs|cjs)` 로 확장. 실측 비용: 가장 넓은 허브 `assembly.mjs` 스테이징 시
16파일 211테스트 **~35s**(이미 있는 project-wide tsc 20~40s 와 같은 급). 이 수치를 훅 주석에
남겨 다음에 "훅이 느리다"고 되돌리려 할 때 근거가 되게 했다.

**교훈**: "테스트가 없다" 보다 **"테스트가 불가능하다 / 트리거되지 않는다"** 가 더 오래 숨는다.
새 표면을 만들 때 그 표면이 CI 에서 **보이는지**를 먼저 확인할 것.

## 5. §6-1 — 부피 산술을 모델에게서 엔진으로 (`f0b1557f`)

전임 문서가 ★단일 최대 병목으로 지목한 축. **거기 적힌 접근 (b) 를 그대로 구현하지 않았다.**

### 5-1. 왜 (b) 가 안전하지 않은가 — 수치로 확인
(b) = "계획 단계에서 loop 면적을 결정론으로 계산해 제시하고 모델은 그걸 쓰게 한다".
그런데 `geometryGate` 가 잡는 것은 산술 오류가 아니라 **"그린 루프 ≠ 의도한 형상"** 이다.
measured 는 루프에서, expected 는 의도에서 나오기 때문에 비교가 의미를 갖는다.
expected 를 루프에서 계산해 주면 **두 값의 출처가 하나가 되어 비교가 항등식이 된다.**

a4-11 의 실패 모양(브리프는 플랜지 50, 그린 루프는 45)을 재구성해 측정:

| expected 출처 | 게이트 |
|---|---|
| 의도(브리프 치수) 360000 | **FAIL** (옳다) |
| 루프에서 유도 340000 | **PASS** — 플랜지 45 부품이 그대로 나간다 |

→ (b) 는 검사가 사라진 것을 개선으로 착각하게 만든다. 3케이스를 회귀로 고정
(`__tests__/expectedVolumeIndependence.test.ts`).

### 5-2. 채택한 것 — 산술만 뺏고 독립성은 남긴다
모델이 못하는 건 **산술**이지 의도가 아니다. `expectedVolume.decomposition` 신설:
모델은 단면을 **브리프 치수로** 항(rect/circle/triangle, sign ±)과 `depthMm` 로 선언하고,
곱셈·합산은 엔진(`volumeDecomposition.ts`)이 한다. 분해는 루프에서 유도하지 않은 **두 번째
독립 진술**이므로 루프와 대조하는 의미가 그대로 남는다.
- decomposition 이 있으면 `valueMm3` 생략 가능 — **안 하는 계산은 틀릴 수 없다.**
- 둘 다 주면 교차검사해 **산술 오류를 기하 오류와 다른 문장으로** 보고한다.
- 부호 조합이 잘못돼 단면적 ≤ 0 이면 부피 0 부품으로 통과시키지 않고 거부.

### 5-3. 실 DeepSeek 실측 (§5-4 방식 — 지표는 완주율이 아니라 **선택 여부**)
비직사각 단면 6브리프 × 3반복 × 2조건 = **decomposition 채택 32/32 (100%)**,
`valueMm3` 를 쓴 계획 **0건**.

남은 실패의 **성격이 바뀐 것**이 소득이다:
- U-채널: 분해(100×10 + 2×10×40 = 1800 × 200 = 360000)가 **맞는데** 그린 루프가 840000
- 각파이프: 분해(3600−2500=1100 × 300 = 330000)가 **맞는데** 루프는 속이 찬 프리즘

산술이 변수에서 빠졌으므로 남은 건 **순수한 작도 오류**다 — 다음 세션이 팔 축이 여기다(§7-1).

⚠ **완주율은 비교하지 않는다.** a4 12브리프 세트는 임시파일이라 남아있지 않고, 이 6브리프는
새로 쓴 것이라 260727 의 10/12 와 **같은 자로 잰 수치가 아니다.** 비교하려면 브리프 세트를
레포에 고정하는 것이 먼저다(§7-2).

## 6. §6-3 — 문서 간 수치 불일치를 소비자 문서까지 (`341f59d7`)

착수 조건이 "**실패 사례를 만들 수 있을 때**"였다(4개 도메인 템플릿이 전부 pass 라서).
그 조건을 **먼저 충족시켰다** — 어셈블리를 위조하지 않고.

`packageConsistencyCheck` 는 **문서가 실제로 인쇄한 숫자를 정규식으로 회수해** 기준과 대조하는
순수 함수다. 서로 어긋나는 문서 집합을 직접 주면 실패 경로가 결정론으로 재현된다. 이 검사에
FAIL 회귀가 **하나도 없었다는 것 자체가 위험**했다 — "여태 FAIL 이 없었다"가 "검출기가
동작한다"의 근거가 되어 있었고, 회수 정규식이 죽어 조용히 통과하는 경우와 구별되지 않았다.

배선 원칙 — **안전 경고와 섞지 않는다.** 정합 불일치는 "형상이 위험하다"가 아니라 "이 봉투 안
문서들이 서로 다른 숫자를 인쇄했다"는 **문서 무결성** 문제다. 섞으면 (a)멀쩡한 형상이
"제작하면 위험"으로 읽히고 (b)진짜 안전 경고가 서류 문제에 묻힌다. ③절에 별도 블록.
- 실패 항목만 나열 · **통과했을 때 "문서가 서로 맞습니다"라고 적지 않는다**(이 검사는 회수
  가능한 숫자만 보고 못 찾은 문서는 스킵하므로 pass 가 "전부 대조했다"를 뜻하지 않는다).
- `error` 면 침묵 — 실패로 둔갑시키지 않는다. 미전달이면 출력 바이트 동일(회귀로 고정).

부수: 쉬운요약 생성을 REV 스탬프·정합 게이트 **뒤로** 옮겼다(웹·MCP 양쪽). 정합 검사는
쉬운요약 자신을 읽지 않으므로 순서 이동이 결과를 바꾸지 않는다.

**여유 1.6배 이하인 것들이 정확히 넘친다** — 개별 사례가 아니라 클래스다.

처방: 전역 60s 는 나머지 23,000여 테스트의 행(hang) 가드로 유효하므로 **올리지 않고**,
무거운 테스트만 `src/test/heavyTestBudget.ts` 의 `heavyTestBudgetMs(격리실측ms)` 로 예산을
유도한다. 인자가 "격리 실행에서 몇 ms 걸렸나" 하나뿐인 것이 요점 — 매직 넘버 대신 **측정치**가
코드에 남고, 값을 바꾸려면 다시 재야 한다. 경합 여유 배수(6)는 한 곳에만 있다.

⚠ **이 클래스는 전수 확인되지 않았다.** 1,792파일 전부의 격리 실행 시간을 재지는 못했다.
새로 무거운 테스트가 들어오면 같은 방식으로 다시 나타날 수 있다 — 나타나면
`heavyTestBudgetMs` 를 grep 해 같은 처방을 붙이면 된다.

## 9. 절차적 교훈

- **"테스트가 없다"보다 "테스트가 불가능하다/트리거되지 않는다"가 더 오래 숨는다**(§2).
  새 표면을 만들면 그것이 CI 에서 **보이는지**부터 확인.
- **인수인계의 진단도 검증 대상이다.** §6-1 의 접근 (b) 는 구현했으면 검사를 없앨 뻔했고,
  §6-4 의 원인 가설(예산 절단)은 실제 실패 모습과 달랐다. 둘 다 **실행해 보고** 알았다.
- **프롬프트에 넣은 문장은 효과를 재라.** 이번에 넣은 경고 하나는 18샘플 A/B 에서 효과가
  없어 되돌렸다. 안 재면 프롬프트는 근거 없이 길어지기만 한다.
- **한 층 아래를 본다**(260727 교훈의 재확인): 검도 리포트 렌더러는 복사할 뻔했으나
  게이트 모듈로 올리는 쪽이 옳았고, 정합 실패 사례는 어셈블리가 아니라 검사기 층에서 만들었다.
