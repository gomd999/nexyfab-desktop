## 2. ★ 왜 이게 오래 살아남았나 — CI 사각지대 2건

회귀를 붙이려다 발견한 것이 결함 자체보다 중요하다.

### 2-1. MCP 엔트리는 vitest 에서 **import 조차 불가능**했다 (`dfe7c9cb`)
`mcp-server.mjs` 를 import 하면 `SyntaxError: Invalid or unexpected token`. 원인은 1행
**shebang** — node 는 `#!` 를 벗겨 실행하지만 vite 변환기는 벗기지 않는다. 즉 이 파일은
**실행은 되는데 CI 는 한 줄도 볼 수 없는** 상태였다(260727 A-5 `87a9e3f2` 와 같은 종류).
레포에 shebang 스크립트가 다수라 파일 하나를 고치지 않고 `vitest.config.ts` 에
`nf-strip-shebang` 플러그인을 뒀다. `#!` 두 글자만 `//` 로 바꿔 **줄 수·문자 오프셋 보존**
(스택트레이스 무손상). 스크립트의 실행 계약(`node mcp-server.mjs`)은 그대로.

### 2-2. pre-commit 이 `.mjs` 엔진 전체를 건너뛰고 있었다 (`81c36d42`)
훅의 vitest 단계가 스테이징 파일을 `grep -E '\.(ts|tsx)$'` 로만 골랐다. 그런데 **소비자 문서를
실제로 만드는 엔진은 전부 .mjs** 다(assembly·package·execution-gate·easy-summary·
domain-dossier-verify·dxf-export·boq·mcp-server…). 도면·BOQ·안전 판정 문서를 만드는 코드를
고치는 커밋이 **관련 테스트를 한 줄도 돌리지 않고** 통과해 왔다.
→ `.(ts|tsx|mjs|cjs)` 로 확장. 실측 비용: 가장 넓은 허브 `assembly.mjs` 스테이징 시
16파일 211테스트 **~35s**(이미 있는 project-wide tsc 20~40s 와 같은 급). 이 수치를 훅 주석에
남겨 다음에 "훅이 느리다"고 되돌리려 할 때 근거가 되게 했다.

**교훈**: "테스트가 없다" 보다 **"테스트가 불가능하다 / 트리거되지 않는다"** 가 더 오래 숨는다.
새 표면을 만들 때 그 표면이 CI 에서 **보이는지**를 먼저 확인할 것.

## 5. §6-1 — 부피 산술을 모델에게서 엔진으로 (`f0b1557f`)

전임 문서가 ★단일 최대 병목으로 지목한 축. **거기 적힌 접근 (b) 를 그대로 구현하지 않았다.**

### 5-1. 왜 (b) 가 안전하지 않은가 — 수치로 확인
(b) = "계획 단계에서 loop 면적을 결정론으로 계산해 제시하고 모델은 그걸 쓰게 한다".
그런데 `geometryGate` 가 잡는 것은 산술 오류가 아니라 **"그린 루프 ≠ 의도한 형상"** 이다.
measured 는 루프에서, expected 는 의도에서 나오기 때문에 비교가 의미를 갖는다.
expected 를 루프에서 계산해 주면 **두 값의 출처가 하나가 되어 비교가 항등식이 된다.**

a4-11 의 실패 모양(브리프는 플랜지 50, 그린 루프는 45)을 재구성해 측정:

| expected 출처 | 게이트 |
|---|---|
| 의도(브리프 치수) 360000 | **FAIL** (옳다) |
| 루프에서 유도 340000 | **PASS** — 플랜지 45 부품이 그대로 나간다 |

→ (b) 는 검사가 사라진 것을 개선으로 착각하게 만든다. 3케이스를 회귀로 고정
(`__tests__/expectedVolumeIndependence.test.ts`).

### 5-2. 채택한 것 — 산술만 뺏고 독립성은 남긴다
모델이 못하는 건 **산술**이지 의도가 아니다. `expectedVolume.decomposition` 신설:
모델은 단면을 **브리프 치수로** 항(rect/circle/triangle, sign ±)과 `depthMm` 로 선언하고,
곱셈·합산은 엔진(`volumeDecomposition.ts`)이 한다. 분해는 루프에서 유도하지 않은 **두 번째
독립 진술**이므로 루프와 대조하는 의미가 그대로 남는다.
- decomposition 이 있으면 `valueMm3` 생략 가능 — **안 하는 계산은 틀릴 수 없다.**
- 둘 다 주면 교차검사해 **산술 오류를 기하 오류와 다른 문장으로** 보고한다.
- 부호 조합이 잘못돼 단면적 ≤ 0 이면 부피 0 부품으로 통과시키지 않고 거부.

### 5-3. 실 DeepSeek 실측 (§5-4 방식 — 지표는 완주율이 아니라 **선택 여부**)
비직사각 단면 6브리프 × 3반복 × 2조건 = **decomposition 채택 32/32 (100%)**,
`valueMm3` 를 쓴 계획 **0건**.

남은 실패의 **성격이 바뀐 것**이 소득이다:
- U-채널: 분해(100×10 + 2×10×40 = 1800 × 200 = 360000)가 **맞는데** 그린 루프가 840000
- 각파이프: 분해(3600−2500=1100 × 300 = 330000)가 **맞는데** 루프는 속이 찬 프리즘

산술이 변수에서 빠졌으므로 남은 건 **순수한 작도 오류**다 — 다음 세션이 팔 축이 여기다(§7-1).

⚠ **완주율은 비교하지 않는다.** a4 12브리프 세트는 임시파일이라 남아있지 않고, 이 6브리프는
새로 쓴 것이라 260727 의 10/12 와 **같은 자로 잰 수치가 아니다.** 비교하려면 브리프 세트를

## 6. §6-3 — 문서 간 수치 불일치를 소비자 문서까지 (`341f59d7`)

착수 조건이 "**실패 사례를 만들 수 있을 때**"였다(4개 도메인 템플릿이 전부 pass 라서).
그 조건을 **먼저 충족시켰다** — 어셈블리를 위조하지 않고.

`packageConsistencyCheck` 는 **문서가 실제로 인쇄한 숫자를 정규식으로 회수해** 기준과 대조하는
순수 함수다. 서로 어긋나는 문서 집합을 직접 주면 실패 경로가 결정론으로 재현된다. 이 검사에
FAIL 회귀가 **하나도 없었다는 것 자체가 위험**했다 — "여태 FAIL 이 없었다"가 "검출기가
동작한다"의 근거가 되어 있었고, 회수 정규식이 죽어 조용히 통과하는 경우와 구별되지 않았다.

배선 원칙 — **안전 경고와 섞지 않는다.** 정합 불일치는 "형상이 위험하다"가 아니라 "이 봉투 안
문서들이 서로 다른 숫자를 인쇄했다"는 **문서 무결성** 문제다. 섞으면 (a)멀쩡한 형상이
"제작하면 위험"으로 읽히고 (b)진짜 안전 경고가 서류 문제에 묻힌다. ③절에 별도 블록.
- 실패 항목만 나열 · **통과했을 때 "문서가 서로 맞습니다"라고 적지 않는다**(이 검사는 회수
  가능한 숫자만 보고 못 찾은 문서는 스킵하므로 pass 가 "전부 대조했다"를 뜻하지 않는다).
- `error` 면 침묵 — 실패로 둔갑시키지 않는다. 미전달이면 출력 바이트 동일(회귀로 고정).

부수: 쉬운요약 생성을 REV 스탬프·정합 게이트 **뒤로** 옮겼다(웹·MCP 양쪽). 정합 검사는
쉬운요약 자신을 읽지 않으므로 순서 이동이 결과를 바꾸지 않는다.

`sparsePCG` 의 벽시계 가드가 비활성이고 수렴은 maxIter/tol 로만 결정된다(결정론).
→ **FEA 예산 상수를 올려도 이 실패는 그대로다.** 경고했던 위험이 여기엔 해당되지 않는다.

## 6-D. §7-1 — 남은 실패는 **작도**다: 게이트가 어느 축인지 말하게 했다

v1 실패 6건을 보니 무작위가 아니었다. U-채널 2건이 **정확히 같은 배수(7/3)** 로 틀렸다:

| 브리프 | 실측 부피 | 분해(선언) | 그린 단면 |
|---|---|---|---|
| b-04 U-채널 | 840000 | 360000 | 외곽 100×50 − 포켓 80×**10** |
| b-12 구멍 뚫린 채널 | 672000 | 288000 | 외곽 80×40 − 포켓 64×**8** |

둘 다 **안쪽 포켓 높이를 '플랜지높이−벽두께' 대신 '벽두께'로** 그렸다. 분해(의도)는 맞다.
부피 비율 하나만 보고하면 이 패턴이 안 보인다 — 그래서 게이트가 불일치를 **깊이 축과 단면
축으로 쪼개** 말하게 했다(`splitVolumeDiscrepancy`):

> volume 840000 mm³ deviates from theoretical 360000 mm³ … — cross-section area: the loop you
> drew encloses 4200 mm² but your decomposition implies 1800 mm² (drawn outer extent 100×50 mm)
> — the loop is not the shape you described

깊이가 맞으면 깊이를 지목하지 않고, 둘 다 맞는데 부피가 다르면 "루프 자체를 의심하라"고
말한다. **판정은 바뀌지 않는다** — 합·불은 여전히 커널 실측 vs 독립 선언으로만 정한다.
그리지 않은 것을 그린 것처럼 고쳐주지 않는다.

### ★ 이 세션에서 가장 중요한 정직 기록 — 완주율이 거짓말을 한 사례
b-08(각파이프)이 실패한 이유는 작도가 아니라 **내가 만든 프롬프트 갭**이었다: decomposition
설명에 "holes 를 선언한 부품의 분해는 구멍을 뚫기 **전**(gross)"이라는 규약을 안 적었다
(기존 `expectedVolume` 설명엔 있었는데 새 필드로 옮기며 빠졌다). 규약을 명시하고 재측정:

- 1회차: b-08 **완주 ✔** — 그런데 **요구 기능 선택 ✘**. 모델이 보어를 아예 선언하지 않고
  속이 찬 60×60×300 프리즘을 만든 뒤 분해도 60×60 로 적었다. 구멍이 없으니 gross=net 이고
  **게이트는 통과한다.** 각파이프를 주문했는데 통짜 각봉이 나온 것이다.
- 즉 **완주율만 봤으면 0/4 → 1/4 을 개선으로 읽었을 것이다.** 이걸 잡은 건 오직
  `requires`/`chose` 지표다 — §5-4 가 완주율 대신 선택 여부를 지표로 세운 이유가 이것이고,
  §7-2 에서 그 지표를 러너에 넣어두길 잘했다.
- 2회차는 다른 사유로 실패(치수). n=2 라 규약 명시의 효과는 **판단 보류**로 남긴다.
  규약 자체는 옳으므로(없으면 각파이프는 원리상 통과 불가) 유지한다.

### ★ §7-5 MCP 감사에서 나온 P0 (`5b1d8616`) — 안전 판정이 예외로 죽으면 "이상 없음"
`mcp-server.mjs` 의 조용한 삼킴 10곳을 훑다가, 그중 둘이 **안전 판정 소스**임을 발견했다:
```js
try { … codeVerification = dv.codeVerificationVerdict(…); } catch { /* skip */ }
try { … domainSafety     = dv2.domainSafetyVerdict(…);    } catch { /* skip */ }
```
`domain-dossier-verify.mjs` 가 던지면 판정이 조용히 null 이 되고, 쉬운요약은 경고 목록이
비었으므로 **"걸린 안전 경고는 없습니다"** 를 인쇄한다. 260723 A-7 이 잡은 것(배선 부재)과
**원인은 다르지만 소비자가 받는 결말은 똑같다.** 웹 라우트도 같은 자리에 `catch (e) { void e; }`
로 동일했다. → `verificationUnavailable[]` 로 기록해 ③절에 별도 블록으로 낸다:
*"이것은 '이상 없음'이 아니라 '확인하지 못함'입니다."* 안전 판정을 날조해 '위험'으로 바꾸지는
않는다 — 판정 안 한 것을 판정한 척 안 하는 것과, 판정 못 한 사실을 숨기지 않는 것은 같은
원칙의 양면이다.

### §7-4 completeness(C1~C9) — **조사했고 착수하지 않았다**(근거 있음)
C1~C9 와 M1~M6 은 실제로 다른 축이다(C=도면 구비요건, M=수치 정합). 그래서 "소비자엔

- `pass:null`(N/A)을 쓰는 항목은 C9 하나뿐이고, C2/C3/C6/C8 은 불린이다. 지금은 GA 생성기가

| 3차 | `fec905b6` | 산출물 생성 실패를 삼킴 | 부재가 **정상으로** → BOQ 없는 묶음이 "원래 그런 것" |

**2차가 가장 나쁘다.** 도면이 부실한 게 아니라 **없는 것**인데, 소비자는 "용접 기호가
빠졌어요 — 어디를 어떻게 붙일지 표기가 필요합니다"라는 **구체적이고 틀린 지적**을 읽는다.
판정이 사라지는 것(1차)보다 판정이 뒤바뀌는 것(2차)이 더 해롭다 — 전자는 침묵이지만
후자는 적극적 오정보다.

처방은 셋 다 같다: **삼키지 말고 "확인 못 함"으로 기록해 소비자까지 전달한다.**
- GA 의존 M3/M5/M6 은 FAIL 이 아니라 N/A + `gaMissing` 플래그. 부품도로 판정 가능한
  M1·M2·M4 는 그대로 판정한다(과소 보고도 하지 않는다).
- 실패 산출물은 `outputsFailed[]` → 쉬운요약 ④절 **파일 목록 바로 옆**(문맥이 거기다).
- 셋 다 미전달 시 출력 **바이트 동일**(하위호환을 회귀로 고정).

## 6-H. 치수 불일치 국소화 — 그리고 **효과가 없다는 것을 확인한 측정**

`d60c1296` 이후 남은 실패를 보니 b-03 L-브래킷이 **3 rep 전부** `measured 8 vs expected 40`
으로 죽었다. 원인은 값이 아니라 **ref 선택**인데 게이트가 숫자만 말했다. §6-D(부피)를 치수에
그대로 적용해, 고른 두 ref 가 월드 X/Y/Z 로 실제 얼마나 떨어져 있는지 함께 싣는다(`67c4689b`).
프리플라이트가 이미 갖고 있던 `refPoints`/`gapAlong` 를 복제하지 않고 `refGeometry.ts` 로
올려 양쪽이 공유한다(이 세션 네 번째 같은 판단).

⚠ **대체 ref 는 제안하지 않는다** — "40 이 나오는 쌍"을 알려주면 모델이 숫자를 맞추려고
의미가 다른 엣지를 고를 수 있고, 그러면 게이트는 통과하고 도면은 틀린다(§6-1 과 같은 종류).

**측정 결과: 완주 20/36 → 19/36 — 즉 변화 없음.** 이건 실패가 아니라 **예측대로**다:
드라이버에 수리 루프가 없어 **모델은 게이트 메시지를 볼 수 없다.** 이 변경의 값은 다음
세션과 사람을 위한 **진단**이지 처리량이 아니다. 그리고 이것이 §7-1(a) 수리 루프의 값을
정확히 말해 준다 — 메시지를 아무리 좋게 만들어도 되먹임 경로가 없으면 0 이다.

### 부수: 대각 쌍은 이미 거부되고 있었다
픽스처를 짜다 확인했다 — 대각 쌍((0,0)↔(8,8))은 측정 엔진이 **먼저** "not-axis-aligned —
use an explicit axis or an aligned dimension" 로 거부한다. 즉 b-03 이 낸 것은 대각 오선택이
아니라 **축정렬인데 엉뚱한 쌍**이고, 그게 숫자로만은 구별되지 않던 바로 그 경우다.

## 9. 절차적 교훈

- **"테스트가 없다"보다 "테스트가 불가능하다/트리거되지 않는다"가 더 오래 숨는다**(§2).
  새 표면을 만들면 그것이 CI 에서 **보이는지**부터 확인.
- **인수인계의 진단도 검증 대상이다.** §6-1 의 접근 (b) 는 구현했으면 검사를 없앨 뻔했고,
  §6-4 의 원인 가설(예산 절단)은 실제 실패 모습과 달랐다. 둘 다 **실행해 보고** 알았다.
- **프롬프트에 넣은 문장은 효과를 재라.** 이번에 넣은 경고 하나는 18샘플 A/B 에서 효과가
  없어 되돌렸다. 안 재면 프롬프트는 근거 없이 길어지기만 한다.
- **한 층 아래를 본다**(260727 교훈의 재확인): 검도 리포트 렌더러는 복사할 뻔했으나
  게이트 모듈로 올리는 쪽이 옳았고, 정합 실패 사례는 어셈블리가 아니라 검사기 층에서 만들었다.
