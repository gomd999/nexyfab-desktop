## 2. 다음 — **P1: 주력 임포트 경로에 커널** ★근거가 가장 확실

### 왜 이것이 1번인가

우리 정체성은 「맞는 것을 수치로」인데, **사용자가 실제로 밟는 경로**
(`/api/nexyfab/drawing/import-step` → `stepToNexyfabAssembly` → `importStepAssembly`)는
전 부품을 **AABB 상자**로 받는다. 리포 자체 회귀에 `최대 58배 과대(ratio 0.017)` 라고 적혀 있다.

정직하게 고지는 한다. 하지만 이제 커널이 실측을 준다 — **정확한 값을 손에 쥐고도 58배
과대를 계속 내보내는 것은 한계가 아니라 모순이다.**

### 설계가 성립한다 — 260801 측정으로 확인

```
트롤리 조립체(7.3MB) → SOLID 205 · SHELL 209 · FACE 8,556
```
`TopExp_Explorer` 로 **솔리드 단위 분해가 된다.** 부품 단위 물량서가 성립한다
(분해가 안 되면 「1부품 64.1kg」이 돼서 못 쓴다 — 그래서 이걸 먼저 쟀다).

### ★확인 완료 — 커널이 **정확 부피·표면적·무게중심**을 준다 (260802 실측)

`measureShapeVolumeProperties` 는 `GProp_GProps` 래퍼를 돌려주고, 값은 `_wrapped.Mass()`
· `.CentreOfMass()` 로 꺼낸다. 정확부피를 아는 형상(⌀100×200 원기둥)으로 대조:

```
부피     1,570,796.327  vs 폐형 1,570,796.327  → 오차  0.000000%
표면적      78,539.816  vs 폐형    78,539.816  → 오차 -0.000000%
무게중심 (0, 0, 100)    — 기대와 일치
```

**메시가 필요 없다.** 이 사실이 설계를 바꾼다:

| 종전 가정 | 실측 후 |
|---|---|
| 커널 = 삼각 메시 → 곡면 부피 **−0.26~−0.62% 과소** | **0.000000%** — 편향이 없다 |
| 7.3MB 파일 메시 **17초** | 메시 불필요 — 질량·물량은 즉시 |
| 메시는 부피 산출의 **수단** | 메시는 **표시 전용**으로 격하 |

⚠ 따라서 `stepKernelImport` 의 「곡면 부피 최대 0.7% 과소」 고지는 **메시를 쓸 때만**
유효하다. 정확 부피 경로로 바꾸면 그 문장을 **함께 고쳐야 한다** — 안 고치면 과소 고지가
남아 「있지도 않은 오차를 있다고」 적는 것이 된다(반대 방향의 과고지).

### 덤으로 풀리는 것 — `composite` 표면적

지금 복합 부품 표면적은 **미산출**이고 BOQ 가 이름으로 고지한다(접촉면을 알 수 없어서).
커널은 표면적도 정확히 준다 — **도장·도금 물량이 처음으로 산출된다.**

### 단계

1. ~~호출 규약 확인~~ **완료(260802)** — 위 표 참조
2. 솔리드 분해 → 부품 배열 (`TopExp_Explorer`, 자식 프로세스 러너 확장).
   각 솔리드마다 **정확 부피·표면적·무게중심**을 함께 낸다(메시는 표시용으로만)
3. `stepToNexyfabAssembly` 가 AABB 대신 커널 부품을 쓰도록 — **AABB 경로는 폴백으로 남긴다**
   (커널 실패 시 종전 동작 + 고지)
4. 회귀: 코퍼스 파일 1개의 부품 수·총질량이 AABB 대비 얼마나 줄어드는지 **수치로 고정**
5. `stepKernelImport` 를 정확 부피 경로로 전환하고 **메시 편향 고지를 함께 정정**
6. `composite` 표면적 산출(도장·도금 물량) — 현재 미산출 고지를 실제 값으로 대체

### ⚠ 성능 예산

부품이 수백 개면 자식 프로세스 1회로 전부 처리해야 한다(프로세스당 WASM 초기화 ~1초).
코퍼스 실측 최대 17,269 부품 — **상한과 대표화 규약**이 필요하다. 상한 초과는
**거부하고 이유를 적는다**(잘라 받으면 형상이 거짓).

### H2 — 그 다음 (커널이 새로 열어 준 길)

**★ 메시에서 파라메트릭으로 되돌아가기 (feature recognition)**

지금 커널 임포트의 근본 한계는 「부피·경계는 실측인데 **치수를 고쳐 재생성할 수 없다**」는
것이다. 그런데 커널은 **면을 종류별로 준다**(실측: FACE 8,556 · `CYLINDRICAL`·`PLANE`·
`CONICAL`·`TOROIDAL` 구분 가능). 그러면 단계적으로 되돌릴 수 있다:

| 단계 | 무엇 | 왜 가능한가 |
|---|---|---|
| ① **홀 인식** | 원통면 쌍 → `holes[{x,y,d}]` | 축·반경이 면에 선언돼 있다 |
| ② **모따기·라운드 인식** | `CONICAL`/`TOROIDAL` 면 → `chamferMm`/`filletMm` | 260801 에 **어휘를 이미 만들었다** |
| ③ **판재 인식** | 평행 평면 2장 + 측면 → `extrude_profile` | 분류기가 이미 하는 일 |

⚠ 이건 **분류기를 다시 짜는 게 아니다.** 지금 분류기는 STEP **원문**을 읽는데, 여기서는
커널이 **정규화한 면**을 읽는다 — 원문 방언·sense 플래그·곡선 종류를 커널이 흡수한 뒤라
훨씬 견고하다. 260801 에 우리가 손으로 고친 것들(sense 플래그·B-스플라인·타원)을
커널이 이미 처리한 상태로 준다.

⚠ **하지만 이건 큰 작업이고, 하기 전에 「필요한가」를 물어야 한다.** 사용자가 임포트한
형상을 실제로 **수정**하는지, 아니면 **물량·검토만** 뽑는지 — §6 측정으로 먼저 확인한다.
수정하지 않는다면 실측 메시로 충분하고, 이 트랙은 통째로 불필요하다.

**그 밖의 H2**

- **정확 무게중심을 구조 검토에 연결** — 전도·지지 판정이 지금은 선언 형상 기반이다.
  임포트 형상은 커널 CG 가 정확하므로 그걸 쓰면 판정이 실물에 붙는다.
- **표면적 미산출 어휘 정리** — `boq.mjs` 에 `return null` 이 4곳이다. 커널이 있는 지금
  몇 개는 산출 가능하고, **불가능한 것은 이유를 유지**한다(과고지 금지).
- **AI 경로 회귀** — §6-2 측정 결과에 따라. 지금은 결정론 경로만 회귀가 있다.

| 부채 | 증상 | 관측 |

## 9. 순서를 정하는 규칙

기능 목록이 아니라 **판단 기준**을 적는다. 다음에 무엇을 할지는 이 규칙으로 정한다.

1. **우리가 파는 것과 실제가 어긋난 것이 최우선.** 기능 부족보다 모순이 더 나쁘다.
   (예: 정확도를 파는데 주력 경로가 58배 과대)
2. **재보지 않은 것은 개선하지 않는다.** 측정이 먼저다 — 이 세션에서 측정 하나가
   우선순위를 통째로 뒤집었다(「OCCT 경로가 필요하다」 → **이미 리포 안에 있었다**).
3. **과고지를 만드는 개선은 개선이 아니다.** 기능을 넣으면 고지도 함께 옮긴다.
4. **큰 작업 전에 「필요한가」를 묻는다.** H2 의 feature recognition 이 그 예다 —
   사용자가 임포트 형상을 수정하지 않으면 통째로 불필요하다.
5. **같은 부류의 사고가 두 번 나면 구조를 고친다.** 한 번은 우회, 두 번은 신호.

기록해 두지 않으면 반복해서 다시 논의하게 된다.

| 항목 | 왜 안 하나 |

## 11. 이 계획을 폐기해야 할 신호

계획이 틀렸다는 것을 **미리 정해 두면** 늦게 깨닫지 않는다.

- §6-1 측정에서 **주력 경로가 이미 잘 되고 있으면** → P1 의 전제가 무너진다(58배는 최악값일 수 있다)
- §6-2 에서 **AI 경로 성공률이 매우 낮으면** → 임포트보다 그쪽이 1번이다

- 커널 도입 후 **패키지 지연이 실사용을 막으면** → 잡 큐(H3)가 H1 으로 올라온다

## 12. 측정 설계 — §6 의 5종을 **어떻게** 재는가

규칙 2번(재보지 않은 것은 개선하지 않는다)이 작동하려면 **방법이 정해져 있어야** 한다.
각 항목에 도구·판정 기준·예상 비용을 붙인다.

### 12-1. 주력 경로 실제 성공률 — **완료(260802)**

```
[주력] {"files":35, "ok":35, "fail":0, "parts":240}
```

**성공률은 문제가 아니었다.** 주력 경로는 다 읽는다. 문제는 충실도다:

```
[충실도] AABB/커널 부피 비 = 0.02 ~ 26.63 (표본 8)
한 파일 대조: 주력 box 28.56×31.5×1.93  vs  커널 경계 63×63×3.0
```

⚠ **AABB 가 형상을 감싸지 못한다** — 과대만이 아니라 **과소도 난다.**
치우친 오차는 보수적으로 쓸 수 있지만 **양방향 오차는 신뢰 구간을 줄 수 없다.**
질량이 작게 나오면 구조 검토가 **안전측이 아니게 된다.** → P1 의 근거는 유지되고 더 분명해졌다.

⚠ 이 측정을 처음 쓸 때 **도구가 틀렸다**: 부품 타입을 `box` 로 가정하고
`width×depth×height` 를 곱해 1 미만 비율이 나왔다. AABB 는 형상을 감싸므로 그럴 수 없다 —
**비율이 물리적으로 불가능하면 도구를 먼저 의심한다.**

### 12-2. AI 경로 성공률 — **다음**

| 항목 | 내용 |
|---|---|
| 무엇 | 자연어 설명 → `textToAssembly` → 게이트 통과 → 부피 산출까지 |
| 도구 | 고정 프롬프트 세트(도메인별 10문장 × 5도메인)를 파일로 두고 반복 실행 |
| 판정 | **게이트 통과율**과 **실패 사유 상위 5** — 통과율 하나로 뭉개지 않는다 |
| ⚠ | LLM 은 실행마다 다르다. **3회 반복의 중앙값**을 쓰고 분산을 함께 적는다 |
| 비용 | 프롬프트 50개 × 3회 = 150 호출. 토큰 비용이 붙으므로 **한 번만** 돌리고 결과를 문서에 고정 |

### 12-3. 임포트 왕복 일치율

| ⚠ | 이건 「임포트가 되나」가 아니라 **「우리가 쓴 것을 우리가 다시 읽나」**다. 안 되면 남에게도 안 된다 |

## 13. P1 실행 설계 (측정 12-1 반영)

### 규약 — 커널과 AABB 를 **섞지 않는다**

| 상황 | 동작 |
|---|---|
| 커널 성공 | 부품 = 커널 솔리드. **정확 부피·표면적·무게중심**을 함께 싣는다 |
| 커널 실패 | **종전 AABB 경로로 폴백** + 「경계 근사이며 오차가 양방향」이라고 고지 |
| 일부만 성공 | 부품마다 `fidelity` 를 붙인다 — 한 어셈블리 안에 두 충실도가 섞여도 **어느 것이 어느 것인지 알 수 있어야** 한다 |

⚠ **총질량 한 줄에 두 충실도를 합산해 적지 않는다.** 합계는 내되 「커널 n개 + 경계근사 m개」를
함께 적는다 — 안 그러면 정확한 합계처럼 읽힌다.

### 회귀 설계 — 무엇이 증명되면 끝인가

1. 코퍼스 파일 1개에서 **부품 수**가 AABB 경로와 같거나 많다(분해가 부품을 잃지 않는다)
2. 총질량이 커널 정확값과 **0.001% 이내**(정확 부피 경로이므로 메시 편향이 없다)
3. 커널을 강제로 실패시키면 **AABB 폴백이 동작하고 고지가 붙는다**
4. `fidelity` 가 부품마다 존재한다(없으면 어느 것이 근사인지 모른다)

### ⚠ 함께 고쳐야 할 것

`stepKernelImport` 의 「곡면 부피 최대 0.7% 과소」 고지는 **메시 경로 전용**이다.
정확 부피로 바꾸면서 안 고치면 **있지도 않은 오차를 있다고** 적게 된다(반대 방향 과고지).

## 18. 면·선 기준 필렛/모따기 — **설계와 한계** (다음)

### 지금 있는 것

| 재료 | 상태 |
|---|---|
| 면 픽킹 규약 | `face-drag` — 뷰어가 **노멀+드래그량**만 보내면 면 명명 → 결정론 패치 |
| 부품 단위 필렛 | `edit-part` 의 `fillet{r}` → `part.filletMm` → **솔리드 전 에지** |
| 커널 엣지 연산 | `s.fillet(r)` · `s.chamfer(c)` (260801 에 모따기까지 배선) |
| 위상 명명 | `topoNaming` + `composedTopo`(시스템 A) · `edgeCorrespondence`(시스템 B) |

### ⚠ 위상 명명 스파이크가 **범위를 이미 정해 놓았다** (ADR-017, 260730 실측)

```
S5 명명 커버리지   extrude 100%  ·  revolve 0%  ·  linearPattern 0%
S5 fillet 결과      0% — fillet 결과는 topo 를 등록하지 않는다
S3 재빌드 생존율    시스템A 100% (264/264)  ·  시스템B 73.5%
S4 앞에 삽입        시스템A 0% (144/144 소실) ·  시스템B 94.4%
postFilletReference NOT SUPPORTED — "fillet: shape has no stable topology"
```

**이게 설계를 정한다:**

1. **압출 기반 부품만** 면·선 필렛을 연다(명명 커버리지 100%).
   `revolve`·패턴은 **0%** 라 참조가 재빌드에서 살아남지 못한다 — **열지 않는다.**
2. **필렛 위에 필렛을 걸지 않는다.** 필렛 결과는 topo 를 등록하지 않아 후속 참조가 불가능하다.
   → 필렛은 **부품 정의의 마지막 단계**로 고정하고, 여러 개는 **한 번에 목록으로** 받는다.
3. **두 명명 시스템의 강점이 반대다**(A=재빌드 100%/삽입 0%, B=재빌드 73.5%/삽입 94.4%).
   하나를 고르지 않고 **A 우선 → 실패 시 B** 로 두되, **어느 쪽이 썼는지 기록**한다.
   ⚠ 어느 쪽도 못 찾으면 **필렛을 걸지 않고 「참조를 잃었다」고 적는다** —
   엉뚱한 엣지에 거는 것이 안 거는 것보다 나쁘다.

### 데이터 형태 (제안)

```
part.edgeOps: [
  { kind: 'fillet' | 'chamfer', r|c: mm,
    ref: { face: '<faceName>', edge: '<edgeName>' },   // 명명 참조
    namer: 'A' | 'B',                                   // 어느 시스템이 찾았나
  }
]
```
`filletMm`(부품 전체)은 **그대로 둔다** — 없애면 기존 사용처가 조용히 깨진다.
둘 다 있으면 **전체 필렛을 먼저, 엣지 필렛을 나중에** 걸고 그 순서를 고지한다.

### 완료 판정

1. 압출 부품의 한 면을 골라 R5 → **그 면에 접한 엣지에만** 걸린다(전체가 둥글지 않는다)
2. 치수를 바꿔 재빌드해도 **같은 엣지**에 남는다(시스템 A 100% 근거)
3. `revolve`·패턴 부품에 요청하면 **거부하고 이유를 적는다**(0% 커버리지)
4. 참조를 잃으면 **필렛 없이 통과 + 고지**(조용히 다른 엣지에 걸지 않는다)
5. 부피·질량이 그만큼 줄어든다(260801 의 볼록 모서리 폐형 재사용)

## 19. 다운로드 HTML 뷰어 — **보기 전용**으로 강화

### 왜 편집을 넣지 않는가

편집은 **게이트·부피·물량 재계산**이 따라와야 한다. 그건 서버 결정론 엔진의 일이고,
오프라인 HTML 에 넣으면 **게이트 없는 편집**이 된다. 그러면 「도면과 물량이 갈린 파일」이
유통된다 — 이 세션 내내 막아 온 바로 그 상태다.

- **사이트 안** = 바꾸는 곳(`face-drag`·`edit-part` 이미 배선됨)
- **다운받은 HTML** = 보는 곳

### 넣을 것 (전부 읽기 전용)

| 기능 | 근거 |
|---|---|
| 부품별 하이라이트·격리 | 205부품 조립체에서 하나를 못 찾으면 무용지물 |
| 부품 정보 팝업 | 질량·부피·표면적·**`basis`(정확값/근사)** — 근거가 형상 옆에 있어야 한다 |
| 치수·경계 토글 | 외형 확인 |
| 계통색 범례 | 이미 색은 있는데 **범례가 없다** |
| 단면 보기(클리핑) | 내부 확인 — 편집이 아니다 |

⚠ `GA_3D.html` 은 **이번 라이브 패키지에서 생성 실패**했다(`outputsFailed: ['GA_3D.html']`).
강화 전에 **왜 실패했는지부터** 봐야 한다 — 없는 것을 꾸미는 것은 순서가 아니다.

## 22. P2 워크플로 묶기 — **설계** (지금까지 「묶는 일」이라고만 적혀 있었다)

### 문제의 정확한 형태

기능이 없는 게 아니다. **한 번에 이어지는 경로가 없다.** 지금은 조각마다 호출이 따로다:

```
/genimage        시안 이미지
/assemble        자연어 → 어셈블리      (오늘 12.5% → 87.5%)
/import-step     실물 CAD → 어셈블리    (오늘 커널 우선으로 전환)
/package         도면·물량·검토·STEP
```

사용자가 **네 번 결정**해야 한다. 경쟁사가 파는 건 기능이 아니라 **한 번**이다.

### 설계 — 새 엔진이 아니라 **오케스트레이터**

```
POST /api/nexyfab/drawing/flow
  { input: { text? , imageBase64? , stepText? }, options }
  → { steps: [{ name, ok, ms, output?, reason? }], assembly, package }
```

**규약 — 이 세션의 불변식을 그대로 적용한다**

1. **단계마다 성공/실패를 남긴다.** 하나가 실패해도 나머지를 진행하고,
   `steps[]` 에 **왜 못 했는지**를 적는다. 「없음」이 「필요 없음」으로 읽히면 안 된다(§16-7).
2. **부분 성공을 성공이라 하지 않는다.** 최종 `ok` 는 **필수 단계**가 다 됐을 때만 참이고,
   선택 단계 실패는 `partial: true` 로 구별한다.
3. **단계별 소요를 싣는다.** 커널 20.6초·AI 8초가 붙으므로 사용자는 **어디서 기다리는지**
   알아야 한다(§14 지연 위험).
4. **되돌아갈 수 있어야 한다.** 각 단계 산출물(어셈블리 JSON)을 그대로 돌려줘서,
   사용자가 3단계만 다시 하고 싶을 때 1단계부터 하지 않게 한다.

⚠ **새 판정을 만들지 않는다.** 오케스트레이터는 기존 라우트를 순서대로 부르는 것이고,
   판정·게이트는 전부 기존 소스가 한다(§16-8: 요약은 새 판정을 만들지 않는다).

### 완료 판정

- 자연어 한 줄 → `steps` 4개가 채워지고 `package` 에 `model.step` 이 들어 있다
- 중간 한 단계를 강제로 실패시키면 **나머지가 진행되고 이유가 남는다**
- 총 소요와 단계별 소요가 응답에 있다

## 23. 운영 준비 — 커널이 프로덕션에 들어갔다

오늘 커널이 **주력 경로**에 들어갔다. 아래는 실측에 기반한 운영 항목이다.

| 항목 | 실측/설정 | 위험 | 다음 |
|---|---|---|---|
| 자식 프로세스 기동 | WASM 초기화 ~1초 | 요청마다 붙는다 | 작은 파일에선 비율이 크다 — 측정 후 임계 결정 |
| 대형 파일 | 7.35MB → **20.6초** | 4회/분 제한과 겹치면 체감 정지 | **§20-4 측정이 먼저** |

**⚠ 동시성 상한이 없는 것이 지금 가장 큰 운영 구멍이다.** 한 프로세스가 수백 MB를 쓰는데
동시 요청을 막는 장치가 없다. 다음에 커널을 건드릴 때 **가장 먼저** 넣어야 한다.

### 무엇을 기록할 것인가 (관측)

- 커널 성공/폴백 비율 — 폴백이 늘면 **커널이 못 읽는 파일이 늘어난 것**이다
- 단계별 소요 p50/p90 — 평균은 쓰지 않는다(꼬리가 문제)
- `outputsFailed` 발생률 — 오늘 `GA_3D.html` 이 걸린 것처럼, **조용한 실패의 조기 경보**다

## 24. 회귀 신호의 건전성 — **24,375 통과가 24,375만큼 의미하지 않는다**

오늘 두 가지가 드러났다. 검사 수를 늘리는 것보다 **신호가 참인지**가 중요하다.

| 문제 | 실측 | 뜻 |
|---|---|---|
| **조건부 skip** | 코퍼스·라이브 게이트 검사 파일 **35개** · 전체 실행에서 **82건 skip** | CI 에서는 이 신호가 **없다**. skip 은 통과가 아니다 |
| **부하에서만 켜지는 게이트** | `phase3PerfBench` 가 `p95 ≥ 0.05` 일 때만 단정 | 한가하면 **검사가 꺼진다** — 성능 회귀를 놓치고, 바쁘면 무작위로 깨진다 |

### 다음

1. **skip 을 눈에 보이게** — 전체 실행 끝에 「skip N건 · 그중 코퍼스 M건」을 요약으로 남긴다.

2. **성능 게이트를 조건부에서 절대 기준으로** — 「부하일 때만 잰다」가 아니라
   **환경을 고정한 별도 실행**으로 옮긴다. 전체 회귀 안에서 시간을 재는 것 자체가 흔들린다.
3. **코퍼스 없이도 도는 대체 신호** — 오늘 만든 두 층 구조(`ai-prompt-contract` 결정론 +
   `ai-path-live` 옵트인)를 다른 코퍼스 의존 검사에도 적용한다.

## 26. 측정 1 결과 — 임포트 지연 (260802)

```
표본 8 (0.01 ~ 3.36MB)   p50 1,341ms · p90 3,073ms · 최대 3,073ms · 15초 초과 0건
별도 실측 7.35MB          20,554ms  ← **임계 초과**
```

⚠ **표본이 3.36MB 까지만 덮었다.** 4~7MB 구간은 재지 않았다 — 그 사이 어디서 꺾이는지 모른다.
「전 구간 빠르다」로 읽으면 안 된다.

관측된 것: `0.01→0.7s · 3.36→3.0s · 7.35→20.6s`. **선형이 아니다**(부품 수에 좌우된다 —
3.36MB 는 1부품, 7.35MB 는 205부품).

### 판단 — 전면 승격이 아니라 **크기·부품 수 기준 분기**

§14 의 「15초 초과 시 잡 큐 승격」이 걸렸다. 다만 **중앙값 1.3초를 잡 큐로 보내면 체감이
나빠진다.** 그래서:

| 경로 | 조건 | 근거 |
|---|---|---|
| 인라인 | ≤ 4MB | 실측 3.36MB = 3.0초 |
| 잡 큐 | > 4MB | 7.35MB = 20.6초. **4~7MB 는 미측정이라 보수적으로 잡는다** |

⚠ 4MB 는 **측정 두 점 사이에서 보수적으로 고른 값**이다. 확정값이 아니며,
4~7MB 를 재면 조정한다. 그 사실을 코드 주석에도 남긴다.

### 함께 드러난 것

- 코퍼스 파일 대부분이 **1부품**이다(단품 모델). 솔리드 분해가 값을 하는 건 **조립체**다.
- 8개 전부 `fidelity: 'kernel-solid'` — 폴백이 한 번도 안 걸렸다.

## 27. 측정 2 + 조치 — 커널 동시성 상한 (260802)

### 실측으로 값을 정했다

```
자식 프로세스 최대 작업집합 = 445 MB   (코퍼스 최대 7.54MB 파일 · WorkingSet64 200ms 폴링)
```

동시 요청 N개 = N × 445MB. 상한이 없으면 요청 몇 건에 서버가 죽는다.

| 설정 | 값 | 근거 |
|---|---|---|
| `KERNEL_MAX_CONCURRENT` | **2** (env 로 덮어쓰기 가능) | 2 × 445MB ≈ 890MB + 서버 자체 |
| `KERNEL_QUEUE_WAIT_MS` | **45초** | 실측 지연 p50 1.3초·대형 20.6초 — 앞선 2건을 기다릴 만한 값 |

⚠ **컨테이너 메모리 할당량을 모른 채** 고른 보수적 값이다. 할당량을 알면 조정한다.

### 규약

- 슬롯을 못 받으면 **기다리지 않고 사유와 함께** 돌려준다 → 호출측이 AABB 로 폴백하고
  「혼잡해서 근사로 받았다」고 고지한다. **조용히 느려지는 것보다 근사임을 알리고 빨리** 준다.
- 폴백 사유가 **「커널 실패」인지 「혼잡」인지 구별**된다. 안 그러면 운영에서 원인을 못 찾는다
  (못 읽는 파일이 는 것인지 부하가 는 것인지).

### ⚠ 가장 위험한 실패 — 슬롯 누수

한 번이라도 새면 상한이 **영구히 줄고**, 끝내 모든 요청이 폴백으로 떨어진다.
**조용한 품질 저하**라 아무도 모른다. 그래서 회귀가 실패·예외 경로에서도 반납되는지 본다
(`kernel-concurrency.test.ts` 4건).

### 남은 것

- 컨테이너 메모리 할당량 확인 → 상한 재조정
- **4~7MB 구간 미측정**(§26) → 인라인/잡 큐 분기점 4MB 는 잠정값

| 1 | 「측정 도구가 틀렸다」 | **LLM 편차**였다 |
| 2 | 「결측 4/4 → 0/4 고쳤다」 | **n=4 의 운.** 3회 중앙값에서 재발 |
| 3 | 「100%」 | 분모가 52→32 로 준 **선택 편향** |
| 4 | 「분모 유지 안 됨」 | 3회 중 **2회 유지**, 1회는 일시 오류 |
| 5 | 「50장이면 신뢰할 수 있다」 | **측정이 호출 한도를 소진**해 무효화 |

### ★ 규칙으로 굳힌다

- **비율만 보지 않는다.** `분모`·`apiErrors`·`타입 분류`를 **항상 함께** 읽는다.
  분모가 줄어든 100% 는 개선이 아니라 선택 편향이다.
- **측정에도 예산이 있다.** 넘으면 측정이 대상을 망가뜨린다(50장 실행이 앞쪽 버킷만
  성공하고 뒤쪽이 통째로 0 — 케이스 종류가 아니라 **실행 순서**를 따라 실패했다).
- **입증 안 된 기능에 호출을 3배 쓰지 않는다** → `EXTRACT_MAX_ATTEMPTS = 2`.

### 남은 것

- 이 지표는 **한도가 회복된 뒤 한 번만** 신중히 재측정한다(50장 1회).
- `temperature: 0` 이라 **같은 요청 반복은 무의미**하다 — 재시도는 요청을 바꿔야 한다
  (빠진 필드 지목 + **타입 고정**). 타입 고정 없이 힌트만 주면 분류가 흔들린다.

## 29. 5도메인 판정 커버리지 — **실측** (260802, §20-5 완료)

도구: `domain-audit.mjs`(표시 계층을 거치지 않고 검사 트리 원본을 순회). 템플릿 54종 전수.

| 도메인 | 템플릿 | **판정** | 입력대기 | 판정불가 | **판정 0개** | 미도달 |
|---|---|---|---|---|---|---|
| interior | 9 | **50** | 25 | 6 | 0 | 0 |
| mech | 18 | 33 | 0 | **32** | 1 | **1** |
| landscape | 8 | 25 | 2 | 4 | 0 | 0 |
| building | 10 | 18 | 1 | **10** | 3 | 0 |
| bridge | 6 | 15 | 2 | 2 | 2 | 0 |
| **civil** | 3 | **0** | 0 | 0 | **3** | 0 |

### ⚠ 숫자를 그대로 읽으면 틀린다 — 확인한 것

`civil` 이 판정 0개지만 **비어 있지 않다.** `auditTemplate` 로 파고드니:
```
retaining_wall_run       reachedVerification {ok:true, decisive:true}   label null
box_culvert              reachedVerification {ok:true, decisive:false}  label null
retaining_wall_alignment reachedVerification {ok:true, decisive:true}   label null
```
**계산기 검증(`/verify`)은 도달하고 결정적**이다. 없는 것은 **안전검토 모듈**이다 —
`runDomainSafetyCheck` 의 디스패치에 **`civil` 분기가 아예 없다**(interior·landscape·
building·bridge·mech 는 전용 모듈이 붙어 있다).

즉 「검토가 없다」가 아니라 **「안전검토 계층이 없다」**이고, 계획도 그에 맞춰야 한다.
(그 구별 없이 「판정 3종 추가」로 짜면 이미 있는 걸 또 만든다.)

## 30. 도메인별 할 일 (실측 근거)

### 30-1. `civil` — **안전검토 모듈이 없다** ★가장 명확한 공백

5도메인 중 유일하게 `runDomainSafetyCheck` 분기가 없다. 계산기(옹벽 안정·암거 라멘)는
있으므로 **새 계산이 아니라 안전검토 계층 배선**이 일이다.

붙일 후보 — **형상이 답을 갖고 있는 것만**(이 세션 규약):
| 검토 | 형상에서 나오는가 |
|---|---|
| 옹벽 저판 폭 / 벽고 비 | ○ (형상 파생) |
| 저판 두께 / 벽고 비 | ○ |
| 앞굽·뒷굽 길이 균형 | ○ |
| 암거 벽두께 / 내공 비 | ○ |
| 시공이음·신축이음 간격 | 선언 필요 → **입력 요구**로 |
⚠ 전도·활동·지지력은 **이미 계산기가 한다** — 중복 구현 금지.

### 30-2. `mech` — 판정불가 32건이 판정 33건과 맞먹는다

절반이 「판정할 수 없다」로 나간다. **다음 작업은 만들기가 아니라 세기다**:
판정불가 32건을 **이름으로 뽑아 분류**한다 — ①하중 미선언(정상) ②계산기 부재(추가 대상)
③적용범위 밖(정상). ①③이 대부분이면 지금이 맞고, ②가 많으면 그게 다음 일감이다.

⚠ **미도달 1건**이 있다 — 계산은 되는데 소비자 문서에 안 닿는 형태 ①이다. 이름부터 찾는다.

### 30-3. `building` — 판정불가 10 · 판정 0개 3

`water_tank`·`elevator_shaft`·`gable_house` 가 판정 0개다. `water_tank` 는 실측에서
「벽식 횡력 검토」로 디스패치되고 **연직 하중경로는 적용범위 밖**으로 명시된다 —
즉 **의도된 거절**일 수 있다. `civil` 과 같은 방식으로 **하나씩 파고들어야** 한다.

### 30-4. `bridge` — 판정 0개 2 (`girder_bridge`·`tapered_girder_bridge`)

⚠ `girder_bridge` 는 과거 「판정: INPUT」으로 계속 찍히던 이력이 있다(코드 주석).
**입력 대기인지 판정 부재인지** 구별이 먼저다.

### 30-5. `interior` — 입력대기 25건이 가장 많다

판정 50 대비 입력대기 25. 「입력만 주면 판정된다」는 뜻이라 나쁘지 않지만,
**사용자가 그 25개를 어떻게 아는가**가 문제다. 오늘 패키지에 넣은 `summary.json`·
`00_안내.html` 처럼 **필요 입력을 한 곳에 모아 보여 주는 것**이 다음 일이다.

### 30-6. `landscape` — 유일하게 판정 0개·미도달이 모두 0

지금 상태가 가장 건강하다. **추가 작업 없음** — 여기서 뭘 더 하는 것은 근거가 없다.
