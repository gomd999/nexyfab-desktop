# Complex-product holdout acquisition

## Purpose and current state

The legacy v2 benchmark requires 20 independent product lineages for each of
six complex-product families. Its frozen corpus currently has 88 of 120 cases.
The original 32 missing slots are robot 11, gearbox 3, pressure vessel 9, and
turbomachinery 9. Ground-truth approval remains 0/88.

The primary mechanical portfolio now promotes seven mechanical families while
`interior` remains an auxiliary Spatial Labs family. `machine_skid` and
`welded_enclosure` are independent promotion units, not aliases that can borrow
`factory_equipment` evidence. Their pending-only extension queue contains 20
slots each. Mechanical coverage is therefore 68/140 and the total shortfall is
72: the original 32 plus the new 40. A single family may graduate through its
own `verified-*` release channel without waiting for unrelated families.

The canonical
`docs/evidence/complex-holdout-lineage-v2-260807/shortfall-acquisition-queue.json`
contains acquisition slots only. It is not CAD storage, evidence of acquisition,
an approval, or a score-eligible corpus. Do not edit it when a source arrives.

## Security boundary

Keep source CAD, license captures, extraction receipts, and review artifacts in
a controlled directory outside both the application repository and every model
development workspace. The v2 validator rejects an intake root that contains,
or is contained by, the workspace. It also rejects absolute/non-canonical paths,
symlinks or junctions, and files whose recomputed size or SHA-256 differs.

Record the release-candidate freeze before acquiring or opening any source.
The freeze receipt binds the release commit, freeze time, exact queue bytes, and
exact existing-cases bytes. New files must remain excluded from training,
fine-tuning, and prompt development, with evaluation-only access already in
effect when acquisition occurs.

Use CAD from a manufacturer, owner, or another source whose terms explicitly
allow the intended commercial evaluation. Do not use screenshots, videos,
PDF-only drawings, AABB approximations, or CAD regenerated by the model under
evaluation as sole ground truth. A queue slot does not authorize copying a file.

## Create a fail-closed 32-slot draft

Generate the draft directly from the canonical queue and frozen 88-case corpus:

```powershell
npm run evidence:holdout-acquisitions:scaffold -- `
  --out=D:\controlled-holdout\submission-v2.json
```

The command writes every current slot ID and family plus SHA-256 bindings for
the queue and cases inputs. It refuses to overwrite an existing draft. All
evidence fields are empty, all isolation controls are false, and every decision
is `pending`; therefore the draft cannot pass validation or imply approval.

The machine-readable contracts are:

- `docs/process/schemas/holdout-acquisition-submission-v2.schema.json`
- `docs/process/schemas/holdout-acquisition-receipts-v1.schema.json`

Pending-only receipt worksheets are in
`docs/process/templates/holdout-acquisition/`. They deliberately contain blank
hashes, false controls, and `pending` decisions, so none validates as evidence
until populated by the corresponding controlled system.

For the 40-slot Machine/Skid and Welded/Enclosure extension, use a separate
controlled draft and the checked-in extension queue:

```powershell
npm run evidence:holdout-acquisitions:scaffold -- `
  --queue=docs/evidence/complex-holdout-lineage-v3-extension-260812/shortfall-acquisition-queue.json `
  --out=D:\controlled-holdout\verified-family-extension-v3.json
```

This file also starts with blank evidence, false isolation controls and pending
decisions. It is an acquisition worklist, not evidence that 40 CAD files exist.

## Intake layout and binding chain

All `relativePath` values are relative to the single controlled intake root.
A practical layout is `sources/`, `licenses/`, `receipts/`, and `reviews/`.
Every artifact reference contains `relativePath`, `bytes`, and `sha256`; the
validator reads the referenced file and recomputes both values.

For each slot, complete this chain:

1. Map one genuinely independent product lineage to the exact queue slot and
   record the immutable original CAD bytes, authoritative HTTPS source,
   provider product ID, acquisition time, and source SHA-256.
2. Capture the applicable license/terms as an immutable artifact. A provenance
   review attestation must bind its hash and the source hash. `approved` may be
   entered only from the controlled review system.
3. Preserve an isolation receipt bound to the slot, family, source hash,
   effective time, access-policy ID, and all four exclusion controls. Use a
   reviewer different from the provenance and native-structure reviewers.
4. Run the governed native extractor and preserve a receipt that binds its
   name, version, executable artifact hash, source hash, and native definition,
   occurrence, transform, and joint counts. Copy those counts into the
   submission; disagreement is rejected.
5. For a conditional format, add a format review. For ZIP, also add a scanned
   member manifest. Traversal paths, links/non-files, encrypted members,
   executable payloads, duplicate names, more than 100,000 entries, more than
   100 GiB expanded data, or greater than 100:1 expansion are rejected.

Archive files and extracted members are one lineage. A source hash, lineage,
relative path, normalized source URL, or provider/product identity cannot be
reused to fill another slot. The validator also compares hash and lineage with
all 88 frozen cases.

Review attestation files must use
`nexyfab.holdout-review-attestation.v1` and contain the trusted review system's
signature-verification result. Do not type `verified` or `approved` by hand.
The local validator verifies the attestation file hash and all bound fields; the
review system remains responsible for authenticating the signer and producing
the signature-verification receipt.

## Validate without promoting

```powershell
$env:NEXYFAB_HOLDOUT_ACQUISITION_ROOT = 'D:\controlled-holdout'
npm run evidence:holdout-acquisitions:validate -- `
  --submission=D:\controlled-holdout\submission-v2.json `
  --out=D:\controlled-holdout\validation-v2.redacted.json
```

Keep the output in the controlled area during intake. The validator emits only
slot/family results and issue codes; it redacts source URLs, product IDs,
artifact paths, reviewer identities, signatures, and absolute paths. It exits
non-zero until all 32 slots pass. A passing receipt means
`readyForCuration=true`; `grantsGroundTruthApproval` and `scoreEligible` always
remain false.

## Promotion sequence

1. Resolve every validator issue without editing original bytes or backdating
   acquisition, isolation, extraction, or review times.
2. Build assertion graphs and tolerance policies from the acquired sources.
3. Run the existing ground-truth queue and domain/independent dual review.
4. Recheck lineage isolation and campaign split before any model execution.
5. Promote only approved cases into a new immutable corpus version; do not
   replace the current evidence corpus in place.
6. Run the 120-case campaign without exposing expected answers to the model.

Neither scaffolding nor a passing intake validation is evidence that the 32 CAD
files have been obtained, that their licenses are approved, or that they are
benchmark ground truth.
